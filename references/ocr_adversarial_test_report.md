# OCR 失真與非典型排版壓力測試報告

## 測試範圍

本次以模擬截圖 OCR 產出的文字進行壓力測試，涵蓋表情符號、全形數字、錯字、訊息斷行、姓名與品項同列、標籤包住姓名、價格與包裝規格，以及沒有明確數量的詢問。這是解析器邏輯測試，不等同於對真實圖片執行 Tesseract OCR；目前工作區沒有新的聊天截圖可供逐張辨識。

## 結果摘要

初始壓力測試產生 8 筆解析列、10 份數量；加入清理與跨行合併後，更新測試產生 **9 筆解析列、11 份數量**。`--source text` 與 `--source ocr` 的訂單列相同；使用 OCR 模式時，所有列都正確標示 `confidence: check`。

| 情境 | 觀察結果 | 判定 |
|---|---|---|
| `🍎 蘋果 + 1` | 表情符號從姓名候選移除，解析為姓名「小美」、品項「蘋果」 | 改善後通過，需覆核 |
| `阿華🎉 香蕉＋２` | 表情符號從姓名候選移除，保留姓名「阿華」 | 改善後通過，需覆核 |

## 目前極限

目前解析器對「姓名與品項同列」的拆分，在姓名與品項之間使用冒號或空白時效果較好；冒號會優先於品項規格判斷，因此 `小芳：青龍6粒198—一份` 可拆出姓名與完整規格。前一行以 `+`／`＋` 結尾、下一行為純數字時，會先合併再解析；若數量被切在一般文字中間、跨越時間訊息，或 OCR 同時改寫了加號與數字，仍需人工確認。

表情符號與外層團購標籤現在會從姓名候選清除；品項兩端的裝飾符號也會清除，但品項內部文字與規格會保留。錯字如 `草莓十1` 仍會被保守忽略，避免在無法確認數量時自行補單。

## 建議後續優化

後續仍可加強 OCR 常見錯字的人工字典、跨越時間訊息的行合併，以及更複雜的多欄截圖版面分析；這些功能不宜在缺乏上下文時自動猜測，以免把詢問誤判成訂單。

實際出貨前仍應確認每筆的 `person`、`item`、`qty` 與 `confidence`；任何 OCR 來源或同列拆分結果都應視為待覆核草稿。
