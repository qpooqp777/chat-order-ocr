# OCR 失真與非典型排版壓力測試報告

## 測試範圍

本次以模擬截圖 OCR 產出的文字進行壓力測試，涵蓋表情符號、全形數字、錯字、訊息斷行、姓名與品項同列、標籤包住姓名、價格與包裝規格，以及沒有明確數量的詢問。這是解析器邏輯測試，不等同於對真實圖片執行 Tesseract OCR；目前工作區沒有新的聊天截圖可供逐張辨識。

## 結果摘要

測試輸入共產生 **8 筆解析列、10 份數量**。`--source text` 與 `--source ocr` 的訂單列相同；使用 OCR 模式時，所有列都正確標示 `confidence: check`。

| 情境 | 觀察結果 | 判定 |
|---|---|---|
| `🍎 蘋果 + 1` | 品項與數量正確，但表情符號被當作訂購人 | 需覆核 |
| `阿華🎉 香蕉＋２` | 全形數量可辨識，但姓名保留表情符號 | 需覆核 |
| `【團購】王姐` | 可沿用作訂購人，但標籤未清理 | 需覆核 |
| `櫻桃 2公斤+1 🛒` | 重量規格保留，訂單可辨識 | 通過 |
| `小芳：青龍6粒198—一份` | 未正確拆出「小芳」，整段被視為品項 | 需改善 |
| `淑仔：文旦100元+\n1` | 數量跨行後未形成可解析訂單 | 需改善 |
| `小強 西瓜+1` | 姓名與品項同列正確拆分 | 通過，需覆核 |
| `甜美人40元＋２盒` | 品項、價格與數量正確保留 | 通過 |
| `草莓十1` | 非標準錯字／數量寫法未辨識 | 正確保守略過 |
| `水梨一盒` | 中文數量與包裝單位可辨識 | 通過 |
| `請留芭樂🙏` | 沒有明確數量，未產生訂單 | 通過 |

## 目前極限

目前解析器對「姓名與品項同列」的拆分，在姓名與品項之間使用冒號或空白時效果較好；但若品項前綴同時包含重量、價格或包裝資訊，保守的規格防誤拆條件可能使整列無法分離，例如 `小芳：青龍6粒198—一份`。跨行數量也需要先由 OCR 前處理合併，否則 `+` 與數字分屬不同訊息列時不會被視為同一筆訂單。

表情符號目前會被保留在姓名候選中。這不會默默遺失訂單，但會使人名不乾淨；帶有括號、團購標籤或其他前綴的姓名也需要額外清洗規則。錯字如 `草莓十1` 則會被保守忽略，避免在無法確認數量時自行補單。

## 建議後續優化

第一，新增 Unicode 表情符號與常見裝飾字元清洗，只在姓名候選上移除，不改動品項原文。第二，將冒號拆分優先於規格防誤拆，例如先辨識 `小芳：` 為姓名，再對右側品項保留 `青龍6粒198`。第三，新增 OCR 行合併階段，把前一行結尾為 `+`、`＋` 或數量前綴、下一行為純數字的內容合併後再解析。第四，將「帶有標籤的姓名」標示為 `check`，而不是直接視為高信心姓名。

實際出貨前仍應確認每筆的 `person`、`item`、`qty` 與 `confidence`；任何 OCR 來源或同列拆分結果都應視為待覆核草稿。
